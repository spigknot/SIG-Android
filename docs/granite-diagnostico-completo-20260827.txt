PROBLEMA 1: "Transcricao vazia" com áudio EN de 71KB (~6,6s)
================================================================================
Sintoma: Processo chega a 100%, mas retorna string "" e a Activity lança
  IllegalStateException("transcrição vazia em ...") (GraniteActivity.kt:521).

CAUSA RAIZ (confirmada):
  O attention_mask enviado ao ONNX Runtime está INVERTIDO.
  
  Em GraniteEngine.kt, linhas 661-663:
    val mask = LongArray(windowFrames) { 1L }   // INICIALIZA TUDO COMO 1 (padding)
    mask.fill(0L, 0, windowLen)                 // PREENCHE [0,windowLen) COM 0 (real)
  
  Resultado:
    frames reais [0, windowLen): mask = 0  (o grafo trata como padding)
    frames de padding [windowLen, 512): mask = 1 (o grafo trata como real)
  
  O grafo ONNX foi exportado de transformers (export_onnx.py linha 31), que usa a
  convenção padrao HF: 1=real, 0=padding. Referencias:
    - modeling_granite_speech5.py:50-55 (docstring: "1 for tokens that are not masked")
    - modeling_granite_speech5.py:88 (atencao aditiva: attn_weights + attention_mask)
    - modeling_granite_speech5.py:629 (sequences[~attention_mask] = pad_token_id)
  
  Com a mascara invertida:
    1. O conformer mascara os frames validos → softmax colapsa
    2. Logits degeneram → argmax sempre escolhe blank (id=0)
    3. ctcCollapse() remove todos (todos são blank) → IntArray vazia
    4. decode([]) → ""
    5. Activity lança "transcrição vazia"

  Por que os testes JVM passam? GraniteEngineTest.kt testa o decoder (ctcCollapse,
  decode) isoladamente, mas NUNCA testa a construcao da mascara. O bug só manifesta
  na ORT inference (transcribeFileInner), que nao tem teste JVM.

  Por que o PC (validate_pipeline.py) passa? Porque lá a mascara é CORRETA (1=real),
  e PyTorch == ONNX é validado com a mascara certa. O bug so existe no Kotlin.

FIX PROPOSTO (nao aplicado):
  GraniteEngine.kt linha 663-664:
    // ANTES (errado):
    val mask = LongArray(windowFrames) { 1L }   // 1 = padding
    mask.fill(0L, 0, windowLen)                 // 0 = real
    // DEPOIS (correto - convenção HF):
    val mask = LongArray(windowFrames) { 0L }   // 0 = padding
    mask.fill(1L, 0, windowLen)                 // 1 = real

  Vacina: adicionar teste JVM em GraniteEngineTest.kt que verifica a mascara
  construction (frames reais = 1, padding = 0, contagem correta).

PROBLEMA 2: OOM com áudio de 19MB (~19s, formato mp3 conforme imagem)
================================================================================
Sintoma (do screenshot): 
  "Erro: Failed to allocate a 81709072 byte allocation with 17915056 free bytes
   and 17MB until OOM, target footprint 268435456, growth limit 268435456"

  - target footprint: 256MB (268435456 bytes)
  - Memoria solicitada: ~78MB (81709072 bytes)
  - Memoria disponivel: ~17MB

IMPORTANTE: Este OOM veio da INTERFACE DESKTOP do SIG (nao Android). O screenshot
mostra "Granite 5.0 Turbo" + "CPU" em uma interface desktop, e o erro e de OOM de
256MB. Isso e um limite configurado na interface Desktop do SIG, NAO no Android.

Analise do codigo Android (para referencia):
  - AndroidManifest.xml: GraniteActivity tem android:largeHeap="true"
    → libera heap maior (tipicamente 512MB+ em Android moderno)
  - GraniteEngine.kt: OrtSession.SessionOptions usa NO_OPT (sem otimizacao)
    → nao aloca buffers extras de otimizacao
  - readWav16kMono (linha 756): carrega WAV inteiro em FloatArray (19s × 16kHz × 4B = ~1,2MB)
    → nao e 78MB. O OOM de 78MB veio de outro lugar (desktop).
  - transcribeFileInner (linha 648-694): janelas de 512 frames fixas
    → cada janela: 512 × 320 × 4B = 655KB de entrada; logits: 128 × 16384 × 4B = 8,4MB

CONCLUSAO PARA O ANDROID:
  O OOM de 19MB nao e um problema do Android (78MB e muito abaixo do heap de 512MB
  via largeHeap). O problema esta NA INTERFACE DESKTOP do SIG, que tem um limite
  de 256MB hardcoded. O audio de 19MB (provavelmente MP3, conforme nome
  "1781383142158_Interview recording 16.mp3") precisa ser convertido/conformado
  antes de rodar pelo ONNX no desktop, e o limite de 256MB e insuficiente.

  No Android, o mesmo problema pode ocorrer se:
    - O FloatArray do WAV for muito grande (mas 19s = 1,2MB, OK)
    - Se o audio for mais longo (ex: 190s = 12MB em FloatArray, ainda OK)
    - O problema real seria o OrtIoBinding ou buffers de logits acumulados no heap

  O fix da mascara (Problema 1) pode reduzir o OOM no Android porque:
    - Argmax distribuido (nao todo blank) → buffers menores no decode
    - Mas o OOM principal no Android seria causado por audio muito longo

FIX PROPOSTO PARA O ANDROID (preventivo, se OOM persistir apos fix da mascara):
  - Chunking: processar o WAV em pedacos de ~16s (256000 frames) em vez de carregar tudo
    → evita FloatArray gigante
  - Usar DirectByteBuffer para o WAV em vez de FloatArray heap-backed
    → move 76MB (19s WAV) para off-heap

  PARA O DESKTOP: investigar onde o limite de 256MB esta configurado. Pode ser
  no codigo do servidor LLM (servidor:8400/v1/chat/completions) ou na propria
  interface Desktop. O desktop nao e este repo Android.

PROBLEMA 3: GPU/NPU falham → fallback para CPU
================================================================================
Sintoma: GPU e NPU dam erros e acabam indo para CPU como fallback.

Codigo (GraniteEngine.kt linha 584-618):
  - Para GPU/NPU: tenta NNAPI (nnapiOptions.addNnapi())
  - Se criar a sessao NNAPI falhar: mostra dialogo perguntando se quer CPU
  - Se o usuario aceitar: cria sessao CPU com NO_OPT

Causa provavel (OnePlus 15):
  - O OnePlus 15 tem onnxruntime OEM no /system/lib64 (libonnxruntime.so 14MB,
    libonnxruntime4j_jni.so 73KB)
  - O fix do fix8 (prepend no nativeLibraryPathElements) resolve o carregamento
    da lib, mas o NNAPI (GPU/NPU) pode falhar por:
    a) Driver NNAPI do OnePlus 15 nao suporta alguma operacao do conformer
    b) O provider NNAPI do onnxruntime-android 1.29.0 tenta usar libnnapi
       do sistema, que pode ter versao incompativel
  - O erro especifico do NNAPI pode ser capturado no catch (linha 602-612)

  O codigo ja tem o dialogo de fallback (linha 460-487 em GraniteActivity.kt:
  onFallbackPrompt pergunta se quer CPU). Isso esta funcionando conforme planejado.

PROXIMO PASsOS PARA GPU/NPU: investigar os logs do logcat para ver a mensagem
exata de erro do NNAPI. Por enquanto, o fallback para CPU esta implementado
corretamente.
