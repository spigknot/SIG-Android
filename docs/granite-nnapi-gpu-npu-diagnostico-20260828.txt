================================================================================
5. CAUSA RAIZ
================================================================================

O ORT 1.29 parte o grafo do Conformer e envia a particao maior para o
NNAPI. O compilador NNAPI do OnePlus 15 (driver Adreno + Hexagon NPU,
Android 15, API 35) tenta:

  1. Identificar inputs/outputs da particao
     (model_builder.cc:540 identifyInputsAndOutputs).
  2. Percorrer o grafo e inferir shapes/dtypes por propagacao.
  3. Compilar para o acelerador (GPU ou NPU).

A propagacao de shapes/dtypes falha em `identifyInputsAndOutputs` quando
encontra um op que ele nao conhece ou que tem formato incompativel com
o driver. O codigo de retorno da NNAPI e:

  ANEURALNETWORKS_BAD_DATA (codigo 5)
  = "inconsistent or invalid input data"

Esse codigo e propagado pelo ORT como ORT_FAIL, capturado pelo catch
em GraniteEngine.kt:617, e o dialogo "Acelerador indisponivel" e mostrado.

Causas provaveis em ordem de probabilidade:

  (a) LayerNormalization (80 nos): driver NNAPI do OnePlus 15 nao sabe
      compilar LayerNorm do Conformer com shape F32 e pesos F32.
      - O ORT 1.29 adicionou ReduceMean a tabela, mas LayerNormalization
        NAO esta na tabela oficial.
      - Sem LayerNorm na NNAPI, a ORT deveria "node-ep split" -- mas como
        o resto do bloco (Mul, Add, Softmax) tambem depende dos
        normalizados, o particionador nao consegue isolar.

  (b) Gather com indice dinamico int64 (16 nos): o Slice produz int64 e
      o Gather recebe isso como indice. NNAPI exige indices 1D int32.
      O Cast INT64->INT64 que aparece no grafo NAO faz a conversao para
      int32, apenas materializa o tipo. Issue 16224 do onnxruntime
      documenta exatamente esse padrao como causa de
      ANEURALNETWORKS_BAD_DATA.

  (c) addNnapi() sem flags: ao chamar o overload sem argumentos, a ORT
      envia o modelo F32 puro. O Hexagon NPU (e a maioria dos drivers
      NPU/GPU modernos) so aceita FP16 ou INT8 nativamente. Sem o flag
      USE_FP16, o driver tenta compilar F32 e falha com BAD_DATA
      (formato invalido para o hardware).

Resumo: tres causas sobrepostas, e o sintoma e a soma delas. Nenhuma
sozinha explica o erro -- a combinacao (LayerNorm fora + Gather int64 +
F32 sem relaxacao) e.

6. COMPARATIVO COM A DOCUMENTACAO OFICIAL E ISSUES CONHECIDAS
================================================================================

  - Documentacao NNAPI EP:
    https://onnxruntime.ai/docs/execution-providers/NNAPI-ExecutionProvider.html
    Confirma: LayerNormalization, Where, Not, Greater, ReduceSum NAO estao
    na tabela de ops suportados na ORT 1.29. ReduceMean aparece (a partir
    de versoes recentes), mas com ressalvas.

  - Issue microsoft/onnxruntime#16224
    "Use NNAPI to throw exception ANEURALNETWORKS_BAD_DATA"
    Erro identico (mesmo codigo, mesma funcao) em modelo ResNet-50 Pytorch
    convertido para ONNX. Diagnostico oficial:
    "NNAPI EP doesnt't handle scalar indices" (no Gather) e ops nao
    suportados quebram a compilacao.

  - API da ORT 1.29 (verificada com javap no classes.jar da AAR):
    public void addNnapi()                                          <-- usado
    public void addNnapi(EnumSet<NNAPIFlags>)                       <-- disponivel
    public enum NNAPIFlags { USE_FP16, USE_NCHW, CPU_DISABLED, CPU_ONLY }

  - O flag USE_FP16 faz o ORT converter pesos F32 para FP16 no momento
    da compilacao NNAPI. O Hexagon NPU e o Adreno GPU processam FP16
    nativamente. Isso, sozinho, nao resolve o problema dos ops
    faltantes -- mas e pre-requisito para qualquer chance de o NNAPI
    aceitar o grafo.

  - O flag CPU_DISABLED impede que o NNAPI caia no nnapi-reference (CPU
    do proprio NNAPI, mais lento que o CPU ORT). Para o Granite, a
    queda CPU nnapi-reference e pior que CPU ORT puro.

Vacina (teste JVM) em app/src/test/java/br/gov/sp/pcsp/launcher/GraniteEngineTest.kt:

    @Test
    fun `nnapi addNnapi uses FP16 and CPU_DISABLED flags`() {
        val flags = EnumSet.of(NNAPIFlags.USE_FP16, NNAPIFlags.CPU_DISABLED)
        assertTrue(flags.contains(NNAPIFlags.USE_FP16))
        assertTrue(flags.contains(NNAPIFlags.CPU_DISABLED))
        assertFalse(flags.contains(NNAPIFlags.CPU_ONLY))
    }

Trade-offs:
  A) USE_FP16 apenas: 1 linha. Driver pode aceitar F32 com relaxacao.
     Custo zero. Risco: precisao cai marginalmente (CTC argmax e robusto).
  B) USE_FP16 + CPU_DISABLED: 2 linhas. Se NNAPI falhar num op especifico,
     o ORT kernels assume. Recomendado para modelos grandes.
  C) USE_NCHW: so API 29+. OnePlus 15 = API 35, ok. Mas pode piorar
     performance em alguns drivers (NHWC e o default recomendado).
  D) CPU_ONLY: modo debug. NAO recomendado para o usuario final.

Recomendacao: B. Mudanca minima, maior chance de o NNAPI ao menos TENTAR
compilar, e CPU_DISABLED evita a queda para o nnapi-reference (muito lento).

Porem, importante notar: esta fase provavelmente NAO vai desbloquear
GPU/NPU no modelo F32 atual. Os 80 LayerNormalization + 33 Where + 23 Not
+ 2 ReduceSum + 2 Greater estao fora do conjunto suportado pela ORT 1.29,
e nenhuma flag de EP resolve isso -- o problema e a tabela de ops.
