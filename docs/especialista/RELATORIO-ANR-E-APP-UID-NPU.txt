B. ANR — ROOT CAUSE + FIX (parecer R4 item 2)
------------------------------------------------------------------------
B1. Stack exato (log 12:30:09): main thread em HyMt2Native.threadCount (JNI)
    <- TextoActivity.translate$lambda$57$lambda$53 (TextoActivity.kt:671) <- main.
    "Input dispatching timed out (Waited 5s)" -> Force finishing -> kill.
B2. Auditoria completa: loadModel/generate seguram o g_mutex por TODA a
    operacao; QUATRO getters chamados na main thread pegavam o MESMO lock:
    threadCount (L671 pos-load), lastStats (L710 pos-generate), lastError,
    backendDescription. Mecanismo: o bloco runOnUiThread pos-load executou
    ENQUANTO o generate (worker) ja segurava o lock => main presa por toda a
    geracao => qualquer toque => ANR. 3 ocorrencias reproduzidas (12:25/12:30/12:37).
B3. FIX APLICADO (diff anexo: docs/npu-hymt2/rodada4/anr-fix.diff):
    - g_mutex INTACTO (semantica preservada; ordem g_mutex->g_ui_mutex).
    - Novo g_ui_mutex protege g_last_error/g_backend_desc/g_last_stats.
    - threadCount: std::atomic<int> g_threads_cache (store no load/release;
      getter le sem lock).
    - TextoActivity: status "Traduzindo..." no fim do load (UI deixa de exibir
      "Carregando modelo..." ate o fim da traducao).
B4. RED-GREEN (EXECUTADO):
    - RED (v1.508): 3 ANRs no cenario "tocar durante load/geracao" — logs +
      traces (/data/anr/anr_30021_2026-10-06-12-37-49-463 etc.) preservados.
    - INCIDENTE (transparencia): o 1o build do fix continha um lock_guard
      DUPLICADO (erro de patch remoto por line-endings mistos) -> deadlock no
      generate. DETECTADO pelo thread-dump (SIGQUIT -> /data/anr/trace_00):
      worker presa em Java_..._generate+3104 -> std::mutex::lock (addr2line:
      lock_guard ctor; objdump: dois locks seguidos de g_ui_mutex). Corrigido
      (6 locks), recompilado, strip, hot-swap (sha+inode verificados).
    - GREEN (lib corrigida): 10 taps durante DUAS geracoes -> PID 7055 estavel,
      0 ANR/Input-dispatching/Force-finishing; traducoes completaram:
