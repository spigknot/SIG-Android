4. CORREÇÕES APLICADAS E PROVAS ANTES/DEPOIS
================================================================================
W07 — Parser WAV (whisper_wav_io.{h,cpp}):
  Antes: pcm.resize(chunk_size/2) sem conferir o tamanho REAL do arquivo →
  OOM/alocação por header forjado; fread sem checagem; múltiplos chunks data
  perdidos; fseek com tamanho declarado.
  Depois: todo chunk limitado ao restante real (erro "chunk WAV declara mais
  bytes que o arquivo"), fread exato, RAII, fmt ≥16 bytes aceitando estendido,
  data ímpar com padding, múltiplos data concatenados em ordem, EOF = erro
  explícito.
  Prova: native-dependencies/tests/whisper/wav_io_test.cpp → 14/14 PASS no
  device (roundtrip, chunks desconhecidos aceitos, fmt curto, dado gigante
  forjado, truncado, ímpar, múltiplos, RIFX, float, 48k, vazio, EOF, fmt 18).

W09 — Cancelamento (whisper_jni.cpp):
  Antes (B0, REPRODUZIDO no device): cancel antes da inferência era APAGADO
  em loadModel/transcribe → inferência inteira rodava: cancel-at load =
  status ok, 1 segmento, 2.692 ms, ok=false; cancel-at pre-infer = 2.661 ms,
  transcrição cheia. Apenas during-infer funcionava (abort_callback, 2.342 ms).
  Depois (C1/C2): 3 barreiras determinísticas (pré-WAV, pré-lock,
  pós-inferência) + beginSession() como fronteira de sessão; cancel nunca
  espera o mutex; pedido consumido no fim (não vaza para a próxima sessão).
  Prova (device): load 79,9 ms / pre-infer 0,206 ms / during-infer 1.714 ms
  → 3/3 status=cancelled, segments=0, texto "Cancelado: transcrição cancelada".

W08 — Callbacks multi-thread (whisper_jni.cpp):
  Antes: JNIEnv* herdado da chamada JNI usado por callbacks que podem vir de
  threads internas do ggml (rastro de crash).
  Depois: JavaVM capturado em JNI_OnLoad; cada callback obtém env próprio via
  GetEnv/AttachCurrentThread (ScopedEnv RAII); callback global com cleanup;
  mutex para o resumo VAD; observabilidade "callbacks=N foreign_thread_callbacks=M"
  na linha native result. Status: compilado e exercitado em TODAS as execuções
  do harness (as provas de cancelamento e os runs passam por este caminho);
  medição explícita do contador: pendente como experimento (não bloqueia).

W10 — Protocolo de resultado (whisper_jni.cpp + WhisperResultParser.kt):
  Antes: texto começando com "Erro:"/"Cancelado:" confundido com controle;
  transcrição vazia = erro genérico.
  Depois: lastTranscribeStatus() → ok/no_speech/cancelled/error; texto vazio
  com inferência OK = no_speech (resultado DEFINIDO, não sucesso silencioso);
  parser Kotlin: status vence prefixo; prefixo só como fallback de lib antiga.
  Testes: WhisperResultParserTest 20 casos.

W05 — Perfis Vulkan (whisper_jni.cpp + harness):
  Trava SIG_WHISPER_VK_PROFILE_LOCK: o produto não reescreve as variáveis
  GGML_VK_* quando o harness assume o controle (sem ela todo A/B V0–V6
  colapsa em V0 — foi EXATAMENTE o que aconteceu na Etapa D da primeira
  rodada, descoberto na segunda). Auditoria: 9/13 variáveis são lidas por
  PRESENÇA ("0" tem o mesmo efeito que "1"); leituras são 1× por processo e
  sobrevivem a whisper_free.

W11 — Vulkan + Flash Attention = SIGABRT (NOVO, REPRODUZIDO 10/10):
  Antes: vulkan+FA on → abort (exit 134) em 10/10 células (B0 e C1, C01 e
  C02), logo após o load, frames dentro de libsig_whisper.so. Este é o
  provável "Vulkan intermitente" do usuário: a variável era a ferramenta com
  FA ligada na GPU.
  Depois (C2): guarda no loadModel força flash_attn=false em backend≠CPU com
  aviso "W11/W12: Flash Attention desativado em GPU…" no load_log.
  Prova (device): C2 vulkan+FA C01/C02 → exit 0, aviso presente,
  "flash attn = 0", transcrição FA-on ≡ FA-off byte a byte; contraponto
  B0 vulkan+FA on = exit 134 (re-confirmado).

W12 — OpenCL + FA = falha silenciosa (NOVO, REPRODUZIDO):
  Antes: opencl+FA on "rodava" mas devolvia no_speech/transcript vazio com
  decoder 0 ms (falha silenciosa de qualidade) — WER 100%.
  Depois: mesma guarda da C2 (aviso no load_log). Resultado: exit 0, WER
  0,109 em C01 com a guarda — sem aceleração (FA em GPU não acelera neste
  driver). NOTA: na Etapa C via --mode core a guarda NÃO é aplicada (caminho
  direto sem JNI) e opencl+fa-compare crashou exit 134 — comportamento do
  caminho de teste, não do produto; registrado.

W13 — Vulkan com FA off devolve transcrição CORROMPIDA (NOVO, ABERTO):
  Vulkan (qualquer perfil) devolve "sopa de tokens" com bytes UTF-8 inválidos
  (WER 0,978 em C01 e 0,992–0,996 em C02). A hipótese era que V1 (fusion
  off) / V2 (graph-optimize off) corrigissem: NÃO corrigem — com a trava
  funcionando (C2, vk_profile_effective diferente por perfil, latência varia
  2,2×: V3 53,0 s … V1 23,8 s), o WER permanece ≈1 em TODOS. O Vulkan é
  8–14× mais lento que a CPU no C01 e ainda produz lixo → candidato a
  correção de produto = backend CPU (já é o default).

W01/W02/W03 — Lifecycle Kotlin (ESTATICO → CORRIGIDO + TESTES):
  Confirmado nos fontes: onDestroy bloqueava a UI com releaseModel() sob o
  mutex de inferência; g_ctx global vs modelLoadLock por-Activity; stop-live
  fazia join(3000) e SEMPRE reabilitava a UI dizendo "finalizada".
  Correção: WhisperSessionController (geração/ownership; releaseAsync com
  executor próprio que só libera se a geração ainda é atual; transcribe e
  callbacks de sessão antiga são descartados; cancel() sem lock algum) +
  WhisperActivity: beginSession() nos 3 pontos de início, callbacks com
  wrapCallback, onDestroy → releaseAsync (zero espera na UI), stop-live com
  re-checagem a 500 ms (teto 30 s) até a thread morrer antes de reabilitar.
  Testes: WhisperSessionControllerTest 12 casos (release fora da thread
  chamadora, geração antiga descartada, cancel não bloqueia com load em
  andamento — latch com timeout 3 s) + WhisperResultParserTest 20 = 32 novos.
