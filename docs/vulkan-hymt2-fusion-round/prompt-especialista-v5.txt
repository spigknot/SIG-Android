PARTE 1 — O QUE JÁ ESTÁ PROVADO (rodada 1)
========================================================================
1. CAUSA-RAIZ: a fusão rms_norm_mul_f32 no Adreno 840 executa mas NÃO escreve
   no destino. Reproducer isolado (sem modelo): X[f32 128,16,T] → RMS_NORM →
   MUL(W[128]). R0=cpu, R1=vulkan separado, R2=vulkan fundido.
     - R1 = R0 bit a bit (6 casas) em 6 padrões
     - R2 = TUDO-ZERO em 6/6 (inclusive fullw sem broadcast, e ones_w)
     - SENTINELA: dst pré-preenchido com 7.0 → R2 devolve tudo-7.0
       (sum=57344, min=max=7.0), R1 devolve o correto (5343.17).
     → o kernel fundido não escreve 1 byte. Compila sem erro, sem crash.
2. SEGUNDA fusão quebrada: add_rms_fusion (rms_norm_partials_f32). Com só a
   1ª vedação, o CHECK passava 667 checks e abortava no 668: RMS_NORM norm-31,
   avg_err=0.606154, result=0 correct=0.817621, pipe=rms_norm_partials_f32
   (partials=1, param3=4, elements=[16,1,1]). Com DISABLE_FUSION=1 passavam
   1290 checks.
3. PATCH PROVISÓRIO: em ggml-vulkan.cpp, só para vendor 0x5143 (Qualcomm):
     (a) disable_fused_rms_norm_mul — veta can_fuse{RMS_NORM,MUL}
     (b) disable_add_rms_fusion — veta o caminho de somas parciais
   Feito por vendor_id, não por chip (1 device testado — ver Q5).
   Observação de processo: a flag (b) foi criada mas o gate esqueceu de
   consumi-la; o CHECK acusou (partials=1 persistiu) e o gate foi adicionado.
4. REGRESSÃO (tudo sem env, gate ativo por padrão):
     - CHECK full 33/33: EXIT=0, 1290 checks, 0 ERROR
     - F16 P/D1/D2: argmax 46/2292/65652 = CPU, top5/margem iguais, 0 NaN
       (P max_abs 0.30, D1 0.08, D2 0.10)
     - Q4_K_M (EOS 120020): EXIT=0, D1 2292, D2 65652
     - app (swap temporário do .so, restaurado depois): Q4_K_M+Vulkan traduz
       curta ("O servidor foi reiniciado.", 8 tok, 33.3 t/s) e média
       (43 tok, 36 t/s) corretamente.
   O F16 foi convertido de um safetensors original; o eos_token_id veio como 3
   (errado) e foi corrigido in-place no offset 5068477 (3 → 120020), tamanho
   3587533760 preservado, sha256 f8c1e74a….

PARTE 3 — Q1.2 (MARCAS IN-SHADER): IMPLEMENTADO + RESULTADO DECISIVO
========================================================================
IMPLEMENTAÇÃO (sem SSBO novo, sem mexer em layout de descriptors):
  rms_norm.comp: nova constante SIG_MARK_STAGE (0=produção, idêntico ao
  original) com 4 pontos de marca, gravados no PRÓPRIO buffer de destino
  (binding já existente), valores negativos |v|>>1 que nunca colidem com
  resultado plausível:
    1 = entrada em main()                        (-1111)
    2 = logo após sum = sumsh[0] (redução feita)  (-2222)
    3 = entrada no ramo do_multiply                (-3333)
    4 = após a primeira escrita em data_d          (-4444)
  vulkan-shaders-gen.cpp: 3 variantes marcadas + 1 de CONTROLE (dup_mul_f32,
  mesmo source, SEM marcas). ggml-vulkan.cpp: 3 pipelines novos + env
  SIGMARK_STAGE=<1..4> e SIGMARK_DUP=1 que trocam o pipeline em runtime;
  SIGMARK_ALLOW_FUSION=1 reabilita a fusão no Qualcomm (o gate padrão a veda)
  para poder medir o defeito.

A/B DECISIVO (todos com SIGMARK_ALLOW_FUSION=1, n_gpu=33, Q4 oficial):
  [base] pipeline rms_norm_mul_f32 ORIGINAL
         → 7 checks, ABORT: avg_err=0.669589 in MUL (check 7)
  [dup]  rms_norm_dup_mul_f32 — MESMO source do rms_norm_f32, MESMA
         especialização {0,1}, compilado como objeto de pipeline SEPARADO
         → 7 checks, ABORT: avg_err=0.669589 in MUL (check 7)  ← IDÊNTICO
  [mark1..4] variantes com marcas
         → 0 checks, SIGSEGV

CONCLUSÃO DO A/B (elimina hipóteses por eliminação):
  ✗ cache de pipeline do driver — o dup falha igual
  ✗ objeto de pipeline reutilizado/shared_ptr corrompido — idem
  ✗ binding/offset errado no dispatch — o dup usa o mesmo caminho de dispatch
  ✗ é o GLSL em si, rms_norm.comp compilado com do_multiply=true, de forma
    determinística. O suspeito primário é a construção
      data_d[d_offset+col] = D_TYPE(scale*data_a[...]*data_b[...])
    com fastmod e do_multiply como constante de especialização.

O PROBLEMINHA (detalhe, é o achado mais forte do Q1.2):
  Duas tentativas de implementar as marcas:
  1ª (índice calculado a partir de gl_NumWorkGroups / d_offset): SIGSEGV nos 4.
  2ª (corrigida — marca SEMPRE em data_d[0], só pelo workgroup (0,0,0), sem
     barreira, valores com |v|>>1): CONTINUA SIGSEGV nos 4.
  Diagnóstico comprovado da 2ª:
    - O switch FUNCIONA — o log imprime
        "SIGMARK| stage=1 -> pipeline_rms_norm_mark_mul_f32"
      e o run para exatamente no primeiro RMS_NORM fundido (node=0, norm-0
      ne=[2048,29,1,1], src1=blk.0.attn_norm.weight buf_off=202982464).
    - O SIGSEGV é no PROCESSO HOST, não há abort do checker nem avg_err/NaN.
      O host morre ao sincronizar/enfileirar depois da 1ª dispatch marcada.
    - O base e o dup (mesmo caminho, shader sem marca) NÃO segfaultam —
      abortam com avg_err 0.669589, o defeito conhecido.
  ASSINATURA:
    Shader sem instrumentação    → executa, resultado ERRADO (avg_err 0.6696)
    Shader com UMA LINHA a mais  → host morre com SIGSEGV
  Isso é a assinatura de compilação no limite / alinhamento de registro no
  driver: o rms_norm.comp com do_multiply=true já compila no limite, e QUALQUER
  perturbação do código (uma linha extra, mais uma specialization constante)
  piora o estado de compilação e produz o pior sintoma possível — em vez de um
  resultado numérico errado, mata o host. Reforça que a correção tem de ser no
  GLSL (ou o contorno se mantém), e que instrumentar ESTE shader no próprio
  driver é arriscado.

  Honestidade: a LEITURA das marcas por estágio ficou impossível (o host morre
  antes). Mas a eliminação via dup/base já entrega a mesma informação. O que
  PRECISA de ser revisto: por que o base/dup não segfaultam mas o shader com
  uma linha a mais sim? Isso é a pergunta que fica.
