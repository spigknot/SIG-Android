O QUE FOI IMPLEMENTADO
----------------------
Instrumentação in-shader SEM SSBO novo e SEM mexer no layout de descriptors, para
não tocar o build de produção. A marca é gravada no PRÓPRIO buffer de destino
(binding já existente), com valores escolhidos para nunca colidir com um
resultado plausível de rms_norm (negativos, |v| >> 1).

  rms_norm.comp: nova constante SIG_MARK_STAGE (0 = produção, idêntico ao
  original) com 4 pontos de marca:
    1 = entrada em main()                          (-1111)
    2 = logo após sum = sumsh[0] (redução feita)   (-2222)
    3 = entrada no ramo do_multiply                (-3333)
    4 = após a primeira escrita em data_d          (-4444)
  vulkan-shaders-gen.cpp: 3 variantes compiladas (mark_f32, mark_mul_f32,
  mul_rope_mark_f32_f32) + 1 variante de controle (dup_mul_f32, SEM marcas).
  ggml-vulkan.cpp: 3 pipelines novos + env SIGMARK_STAGE=<1..4> e SIGMARK_DUP=1
  que trocam o pipeline em runtime; SIGMARK_ALLOW_FUSION=1 reabilita a fusão no
  Qualcomm (o gate padrão a veda) para poder medir o defeito.

RESULTADO DECISIVO (A/B)
------------------------
Todos com SIGMARK_ALLOW_FUSION=1 (fusão ativa, reproduzindo o defeito):

  [base] pipeline rms_norm_mul_f32 ORIGINAL
         → 7 checks, ABORT: avg_err=0.669589 in MUL (check 7)   = defeito
  [dup]  rms_norm_dup_mul_f32 — MESMO source do rms_norm_f32, MESMA
         especialização {0,1}, compilado como objeto de pipeline SEPARADO
         → 7 checks, ABORT: avg_err=0.669589 in MUL (check 7)   = IDÊNTICO
  [mark1..4] variantes com marcas
         → 0 checks, Segmentation fault (ver ressalva abaixo)

CONCLUSÃO
---------
O defeito NÃO é do objeto de pipeline (nem de cache/compilação do driver):
o `dup` é byte-a-byte o mesmo shader, a mesma especialização, o mesmo push
constant e o mesmo binding count, e falha com o MESMO avg_err. O que falha é o
shader rms_norm.comp quando compilado com do_multiply=true, de forma
determinística e idêntica a cada run.

Isso elimina de uma vez as hipóteses:
  ✗ cache de pipeline do driver
  ✗ objeto de pipeline reutilizado/shared_ptr corrompido
  ✗ binding/offset errado no dispatch (o dup usa o mesmo caminho de dispatch)
e mantém como suspeito primário o GLSL em si — a construção de
data_d[d_offset + col] = D_TYPE(scale * data_a[...] * data_b[...]) com
fastmod e a especialização como constante de compilação.

RESSALVA HONESTA — os 4 estágios com marca dão Segmentation fault
----------------------------------------------------------------
1ª tentativa (índice calculado): SIGSEGV em todos os 4 estágios.
2ª tentativa (corrigida): marca escrita sempre em data_d[0], só pelo workgroup
(0,0,0), sem barreira. RESULTADO: continua SIGSEGV nos 4.

Diagnóstico do 2º tentativa (comprovado, não palpite):
  - O switch FUNCIONA: o log imprime
      "SIGMARK| stage=1 -> pipeline_rms_norm_mark_mul_f32"
    e no mark1 o run para exatamente no primeiro RMS_NORM fundido (node=0,
    norm-0 ne=[2048,29,1,1], src1=blk.0.attn_norm.weight buf_off=202982464).
  - O SIGSEGV é no PROCESSO HOST, não há abort do checker nem
    "avg_err"/NaN. Ou seja: o host morre ao sincronizar/enfileirar depois
    da primeira dispatch com o shader marcado.
  - O base (mesmo caminho, shader sem marca) NÃO segfaulta: aborta com o
    avg_err 0.669589, o que é o defeito conhecido.
  - O dup (objeto de pipeline separado, shader sem marca) também não
    segfaulta: mesmo avg_err 0.669589.

Interpretação (é o achado mais forte do Q1.2):
  Shader sem instrumentação    → executa, resultado ERRADO (avg_err 0.6696)
  Shader com UMA LINHA a mais  → host morre com SIGSEGV
Isso é a assinatura de um problema de ALINHAMENTO/registro no driver: a
compilação do rms_norm.comp com do_multiply=true já está no limite, e
qualquer perturbação do código (uma linha extra, uma specialization
constante a mais) piora o estado de compilação e produz falha que nem chega
a ser um resultado numérico errado — mata o host. Reforça que a correção deve
ser no GLSL (ou o contorno deve ser mantido), e que instrumentar este shader
no próprio driver é arriscado.

O QUE ISSO CORRIGE
-----------------
A hipótese que eu havia lançado — "compilação no limite / pressão de registro
no driver" — estava errada e era especulação. O crash NÃO é o host, NÃO é
índice OOB, NÃO é corrupção de descriptor. Os 5 primeiros frames estão TODOS
em libllvm-qgl.so, que é o COMPILADOR DE SHADER do driver Qualcomm, com
x0 nulo e fault addr 0x8: é um NULL DEREF dentro do próprio compilador de
shader, disparado ao compilar a variante instrumentada do rms_norm.comp.

Consequência prática: a técnica de marca in-shader é INVIÁVEL neste Adreno
840 — não é possível instrumentar este shader por dentro. Isso CONFIRMA a
preocupação do especialista (ponto B do Q1.2: "um assert costuma se manifestar
como abort, mas o sinal não substitui o backtrace") e invalida minha
interpretação anterior.

Observação que NÃO deve ser lida como micro causa resolvida: o mesmo driver
compila o shader ORIGINAL sem crash (mas com resultado errado). Portanto o
defeito numérico original e este crash do compilador são dois sintomas
distintos; só o segundo foi localizado.
