1. OBJETIVO DO TRABALHO
--------------------------------------------------------------------------------

Fazer "GPU (Adreno)" e "NPU (Hexagon)" virarem backends REAIS e distintos no
Granite Speech 5.0 TurboCTC local (GraniteActivity/GraniteEngine.kt) do app SIG
Android, usando o QNN Execution Provider (EP) do ONNX Runtime.

Motivação:
- O NNAPI (antigo caminho de aceleração) está deprecado e dava o erro
  ANEURALNETWORKS_BAD_DATA no device.
- A transcrição local do Granite 5.0 (modelo ~470M, ~1,9 GB FP32) roda só em CPU,
  que é lenta. A ideia era usar o Adreno (GPU) e o Hexagon (NPU) do Snapdragon
  8 Elite Gen 5 para acelerar.

Aparelho alvo: OnePlus 15 (CPH2747), Snapdragon 8 Elite Gen 5 (SM8850),
platform "canoe", Android 16 (SDK 36).

Restrições do projeto:
- APK < 10 MB: as libs QNN (QAIRT) e os modelos NÃO podem ir embutidos no APK;
  são baixados sob demanda do Cloudflare R2.
- Não usar NNAPI.
- Fallback para CPU SEMPRE com diálogo de confirmação (nunca silencioso).
- Regra de release: NUNCA gerar release sem pedido explícito do usuário.

4. INVESTIGAÇÃO GPU (ADRENO) — BECO SEM SAÍDA
--------------------------------------------------------------------------------

4.1 Bloqueio 1: StridedSlice rejeitado (RESOLVIDO)
Sintoma (logcat):
  [W:onnxruntime:, qnn_model_wrapper.cc:468 CreateQnnNode] QNN.backendValidateOpConfig()
  failed for node `/model/encoder/Slice` of type `StridedSlice` with error code 3110
  ... (4 nodes por tentativa; depois aborta)
  [E:onnxruntime:, qnn_model.cc:387 FinalizeGraphs] Failed to finalize QNN graph. Error code: 6020

Diagnóstico:
- 3110 = QNN_OP_CONFIG_ERROR — o backend GPU rejeita a config do op.
- O modelo tem 404 nodes Slice. Acontece MESMO com params constantes e steps=1
  (slices simples [0:2], [2:4]... da atenção multi-head; e no-ops [0:512]).

Solução aplicada:
- Script tools/granite/convert_slice_to_gather.py converte TODOS os 404 Slice
  em Gather (400) + Identity (21 no-ops), com índices constantes.
- Primeira versão gerou índices int64; corrigido para int32 (QNN pode exigir).
- Validação numérica (onnxruntime CPU, input aleatório 1×512×320):
  * int64: max abs diff 0.000000 (idêntico)
  * int32: max abs diff 0.000000 (idêntico)
- Modelo publicado no R2 (bucket sig-android):
  granite-5.0-turboctc-fp16-gather.onnx (~947 MB) — HTTP 200 OK.
- Resultado: warnings 3110 SUMIRAM do logcat (todos os ops passam na validação
  de config).

4.2 Bloqueio 2: 6020 persiste na finalização (NÃO RESOLVIDO)
Após remover os StridedSlice, FinalizeGraphs ainda falha com 6020, agora SEM
nenhum warning de op (falha silenciosa na compilação do grafo).

Testes realizados (todos falham com 6020):
1. FP16-gather com índices int64  → 6020
2. FP16-gather com índices int32  → 6020
3. F32-gather (para isolar se o problema era o FP16) → 6020 TAMBÉM

Diagnósticos tentados sem sucesso:
- setSessionLogVerbosityLevel(0) (log VERBOSE do ORT): só mostrou a limpeza de
  initializers não usados; nenhum detalhe do op que falha.
- qnnConfig["log_level"]="2" (log nativo do QNN): não apareceu no logcat.
- enable_framework_op_trace=1 + framework_op_trace_dir: o dir foi criado, mas o
  trace ficou vazio (a falha acontece antes da escrita do trace).

Conclusão (beco sem saída):
- O QNN GPU EP do ORT 1.29 (onnxruntime-android-qnn:1.29.0) NÃO consegue
  compilar/finalizar o grafo do Granite 5.0, seja FP16 ou F32. Não é um op
  específico (todos validam), não é o FP16 (F32 falha igual), não é o Slice
  (removido). É limitação do backend GPU do ORT 1.29 com modelo grande de
  atenção (4000+ nodes, 470M params) — provavelmente memória de grafo/contexto
  ou operação interna que falha silenciosamente.
- Não encontramos flag/config do QNN GPU EP que resolva (backend_path,
  offload_graph_io_quantization, log_level, framework_op_trace — todas testadas).
- Sem root e sem outra versão do ORT testável hoje, o GPU fica como beco.

5. INVESTIGAÇÃO NPU (HEXAGON/HTP) — RESULTADO: FUNCIONA (Turbo), NAR morre por memória
--------------------------------------------------------------------------------

5.1 Bug 1 (RESOLVIDO): htpArchitecture() usava System.loadLibrary
Sintoma: ao selecionar NPU, logcat:
  Load libQnnHtpV81Stub.so ... dlopen failed: library "libQnnHtpV81Stub.so" not found
  (idem v79/v75/v73) → "Arquitetura HTP não detectada neste aparelho."

Causa: System.loadLibrary("QnnHtpV81Stub") procura no diretório nativo padrão
do APK; mas as libs QAIRT ficam em no_backup/qairt/v1/lib (baixadas sob
demanda). O GPU não precisava do HTP arch, por isso só o NPU quebrava.

Fix: htpArchitecture(context) agora usa System.load(caminho completo) do
arquivo no dir QAIRT (QairtDependencyManager.kt). Teste JVM existente
("htpArchitecture order is newest first") não chama a função, então não quebrou.

5.2 Bug 2 (RESOLVIDO): libcdsprpc.so não encontrado
Sintoma: dlopen failed: library "libcdsprpc.so" not found: needed by
.../libQnnHtpV81Stub.so in namespace clns-9.

Causa: o stub HTP precisa da lib FastRPC do sistema (libcdsprpc.so, do
/vendor/lib64) para falar com o DSP. O app não vê /vendor/lib64.

Teste: copiada manualmente libcdsprpc.so + libadsprpc.so do /vendor/lib64 para
o dir QAIRT com permissões corretas (chown u0_a591, chmod 755) → o erro de
libcdsprpc sumiu.

5.3 Bug 3 (NÃO RESOLVIDO): libhidlbase.so e a cadeia de libs VENDOR
Sintoma: dlopen failed: library "libhidlbase.so" not found: needed by
.../libcdsprpc.so in namespace clns-9.

Tentativas:
- Copiadas libhidlbase.so, libhidltransport.so, libhwbinder.so do /system/lib64
  para o dir QAIRT (chown/chmod) → AINDA falha com "libhidlbase.so not found".
- Adicionado NativeDependencyManager.registerNativeLibraryDir(libDir) no
  loadQnnNatives (mesmo mecanismo que registra o dir no nativeLibraryPathElements
  do classloader, que resolve as libs do ONNX Runtime) → AINDA falha.

Causa raiz (beco sem saída):
- O namespace do app (clns-9) no Android 16 NÃO permite dlopen de libs do
  vendor (/vendor/lib64), mesmo quando o arquivo é copiado para o diretório do
  app. O dlopen do libcdsprpc.so procura libhidlbase.so APENAS nos paths
  permitidos do namespace, não no mesmo diretório.
- O qnn-platform-validator funcionava porque roda como root/shell (fora do
  isolamento de namespace de apps) — por isso o smoke test R1 deu PASSED, mas o
  app NÃO consegue.
- Risco R1 do plano ("skel HTP em app sem root pode não carregar") CONFIRMADO:
  em Android 16 sem root, o HTP é inacessível de um app normal. As libs vendor
  (FastRPC/HIDL) são necessárias e bloqueadas.
